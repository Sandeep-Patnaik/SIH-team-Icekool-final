# Module 2 — Database & Query Layer (`database/`)

Owner: Person 2 (Senior Backend/DB Engineer). Branch: `feature/database`.

## Module Overview

This module owns the PostgreSQL schema and is the **only** sanctioned way any
other module touches the database. Every other module (Ingestion, Vector/RAG,
LLM Query Engine, Dashboard, Intelligence Engine) reads/writes through
`database.repository.ProfileRepository` — nobody else imports
`database.models` or opens a session directly.

Two schema sources are kept in sync deliberately:
- `database/schema.sql` — hand-written DDL, the fallback single source of
  truth if Alembic isn't wired into the demo environment in time.
- `database/models.py` + `database/migrations/` — the SQLAlchemy ORM models
  and their Alembic migration history, for anyone who *does* run Alembic.

Both describe the exact same four tables from Part 0 §Database Schema:
`floats`, `profiles`, `measurements`, `reports`.

## File Responsibilities

| File | Responsibility |
|---|---|
| `models.py` | ORM classes matching `schema.sql` exactly, named `Float`/`Profile`/`Measurement`/`Report` per Part 2's spec. `Float` the class does shadow `sqlalchemy.Float`/Python's builtin `float` within `models.py`'s namespace, so the SQLAlchemy column type is imported there as `SAFloat` to avoid the collision — this is internal to `models.py`; no other module imports `database.models` directly (everyone goes through `ProfileRepository`). `id`/`float_id` are never renamed. |
| `session.py` | Lazily-built, process-wide `Engine` + `sessionmaker` from `Config.DATABASE_URL`. `session_scope()` context manager commits on success, rolls back and logs on error, always closes. |
| `repository.py` | `ProfileRepository` — every method returns plain `dict`s, never ORM/`Row` objects, so callers never import `database.models`. |
| `repository_helpers.py` | Private upsert/replace/dict-conversion/haversine helpers used internally by `ProfileRepository`. Split out of `repository.py` to stay under the project's ~300-400 line-per-file cap; not part of the locked public API and not meant to be imported by other modules. |
| `exceptions.py` | `RecordInsertError` (write-path failures), `UnsafeQueryError` (raised by `run_raw_query` on anything but a safe single `SELECT`). |
| `schema.sql` | Raw DDL fallback; includes two indexes (`ix_measurements_profile_id`, `ix_profiles_region_date`) that speed up Module 5/6's common access patterns. |
| `migrations/` | Alembic setup. `env.py` imports `Config.DATABASE_URL` and `database.models.Base` directly — no separate/duplicated connection string in `alembic.ini`. |

## Implementation Plan (as built)

1. `models.py` — ORM classes, matched 1:1 against Part 0's DDL.
2. `session.py` — engine/session singletons + `session_scope()`.
3. `exceptions.py` — custom exception types so callers can catch specific
   failures instead of a bare `SQLAlchemyError`.
4. `repository.py` — `ProfileRepository`, implementing the locked signatures:
   `insert_profile_record`, `get_profiles_by_region`, `get_profiles_near`,
   `get_measurements_for_profile`, `insert_report`, `run_raw_query`.
5. `schema.sql` — DDL fallback, including the two extra indexes.
6. `database/migrations/` — Alembic scaffold (`alembic init`), `env.py`
   rewired to the project's `Config`/`Base`, then one autogenerated initial
   migration, manually amended to add the two indexes that autogenerate
   can't see (they aren't expressed as `sa.Index()` on the ORM models).
7. `tests/database/` — `conftest.py` (in-memory SQLite fixture) +
   `test_repository.py` (25 tests across every repository method).

## Setup Instructions

1. From the repo root, copy `.env.example` to `.env` and set
   `DATABASE_URL` (Postgres in real use). Per Part 0's canonical
   `config.py`, `Config.DATABASE_URL` is `os.environ["DATABASE_URL"]` —
   required, no default — so the app raises `KeyError` on startup if it
   isn't set. For local dev/CI without Postgres, set
   `DATABASE_URL=sqlite:///./oceanmind_dev.db` explicitly in your `.env`
   rather than relying on a built-in fallback.
2. Install dependencies: `pip install -r database/requirements.txt`.
3. Create the schema — pick ONE:
   - **Alembic (preferred):** `alembic upgrade head`
   - **Raw SQL fallback:** run `database/schema.sql` against your Postgres
     instance directly (e.g. `psql $DATABASE_URL -f database/schema.sql`).
4. Sanity-check: `python -m database.session` (opens/closes a session),
   then `python -m database.repository` (runs a full insert/read/upsert/
   raw-query self-test against whatever `DATABASE_URL` currently points at
   — safe to run against a local SQLite `DATABASE_URL`, creates only a
   `SELFTEST_0001` float/profile/report row).

To generate a new migration after changing `models.py`:
```
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```
Always review the autogenerated migration — indexes not expressed as
`sa.Index()` on the models (see `ix_measurements_profile_id` and
`ix_profiles_region_date`) won't be picked up automatically and must be
added by hand, as was done in the initial migration.

## Integration Notes

**Consumes from `shared/`:**
- `shared.schemas.ProfileRecord` — the input type to
  `insert_profile_record`.
- `shared.logger.get_logger` — for all logging in this module.
- `config.Config.DATABASE_URL` — the only place the DB connection string
  is read from. **This is `os.environ["DATABASE_URL"]` — required, no
  default.** An earlier draft of this module's `config.py` had it as
  `os.environ.get("DATABASE_URL", "sqlite:///./oceanmind_dev.db")`, which
  would have silently deviated from Part 0's shared contract when the 6
  module folders were merged; it's been reverted to the canonical
  required form. Every module — not just this one — must ensure
  `DATABASE_URL` is set (e.g. via `.env`) before importing `config`.
  Because this is required at import time, `tests/database/conftest.py`
  sets a placeholder (`os.environ.setdefault("DATABASE_URL", ...)`)
  before importing anything that imports `config` — the placeholder is
  never actually connected to, since the test fixture swaps in a
  throwaway in-memory SQLite engine before every test runs.
- `shared.regions.REGION_NAMES` — not imported directly by this module
  (Module 1 assigns `ocean_region` before a `ProfileRecord` ever reaches
  here), but `get_profiles_by_region`'s `region` parameter and
  `insert_report`'s `region` parameter are both expected to be one of
  these exact strings; this module doesn't validate that itself.

**Produces for other modules — the locked `ProfileRepository` API:**
```python
insert_profile_record(record: ProfileRecord) -> int
get_profiles_by_region(region: str, start: date, end: date) -> list[dict]
get_profiles_near(lat: float, lon: float, radius_km: float) -> list[dict]
get_measurements_for_profile(profile_id: int) -> list[dict]
insert_report(region: str, period_start: date, period_end: date,
              file_path: str, summary_text: str) -> int
run_raw_query(sql: str, params: dict | None = None) -> list[dict]
```
- **Module 1 (Ingestion)** calls `insert_profile_record` — upserts on
  `(float_id, cycle_number)`, so re-running ingestion over the same file is
  always safe and never duplicates a profile. A re-ingested profile's
  measurement list fully replaces the old one (delete-then-insert), since
  the newest ingestion run is treated as the source of truth.
- **Module 3 (Vector/RAG)** may read via `get_profiles_by_region` /
  `get_profiles_near` when building the index from live rows instead of
  Module 1's Parquet mirror.
- **Module 4 (LLM Query Engine)** is the sole caller of `run_raw_query`.
  This layer independently re-validates the SQL (single `SELECT`, no
  semicolons/comments, must reference at least one of
  `floats/profiles/measurements/reports`) as defense-in-depth on top of
  Module 4's own `sql_guard.py` — it never trusts the caller already
  checked.
- **Module 5 (Dashboard)** calls the read methods directly for the map/
  profile views, and reads `reports` rows (inserted by Module 6) for the
  Reports tab.
- **Module 6 (Intelligence Engine)** calls `get_profiles_by_region` /
  `get_measurements_for_profile` to compute the Ocean Health Index, and
  `insert_report` after writing its PDF/HTML report to disk.
- Read methods (`get_profiles_by_region`, `get_profiles_near`,
  `get_measurements_for_profile`) fail soft — they log and return `[]`
  rather than raising, since they're called live from the dashboard.
  Write methods (`insert_profile_record`, `insert_report`) raise
  `RecordInsertError` on failure, since a silent write failure would be
  worse than a visible one during ingestion/report generation.

## Testing Instructions

```
pip install -r database/requirements.txt
pytest tests/database -q
```

25 tests, no external Postgres required — `tests/database/conftest.py`
wires `database.session` to a throwaway in-memory SQLite engine
(`StaticPool` keeps one connection alive for the whole test so `:memory:`
state persists across queries) and rebuilds the schema before every test.

Coverage:
- `insert_profile_record`: basic insert, upsert-doesn't-duplicate,
  measurement replacement on re-ingest, distinct cycles create distinct
  profiles.
- `get_profiles_by_region`: region + date-range filtering, out-of-range
  exclusion, no-match returns `[]`.
- `get_profiles_near`: haversine radius filtering, exclusion outside
  radius, nearest-first ordering.
- `get_measurements_for_profile`: shallowest-first ordering, unknown
  profile returns `[]`, missing BGC fields stay `None` (never `0.0`/NaN).
- `insert_report`: returns a new id.
- `run_raw_query`: valid parameterized `SELECT` executes; rejects
  `DROP`/`DELETE`/`UPDATE`/`INSERT`, stacked statements (`;`), comment
  injection (`--`, `/* */`), empty/blank input, and queries that touch no
  allowed table.

Migration correctness was additionally verified manually (not part of the
pytest suite, since it exercises Alembic's CLI rather than the repository
API): `alembic upgrade head` → inspect tables/indexes → `alembic downgrade
base` → `alembic upgrade head` again, confirming a clean round trip.
